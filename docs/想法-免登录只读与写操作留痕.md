# 想法：免登录只读 + 写操作留痕（未实施）

> 记于 2026-10-20　状态：**一个想法，暂不做**（使用方原话：展示不打算做，但担心忘记）
>
> 起因（使用方原话）：
> 「默认不需要登录，可以使用所有功能，但是遇到增删改数据库或是文件库的操作，会提示联系管理员。
> 而且此次操作会被记录。…记录谁？用户名（所以要新增一个注册功能）和IP。
> …是不是涉及 AOP 或是钩子，这样效果更高，还是我已经落伍了，前沿的编程技术有没有更好的更优异的方法」

---

## 一、这想法其实是两件事，别混在一起

1. **授权**：能不能写；
2. **审计**：想写的人记下来。

混在一起的后果是"拿 AOP 去拦所有请求" —— 那样既慢，又会把读请求也记进审计表。

## 二、现状盘点（很多已经有一半了）

| 能力 | 现状 |
|---|---|
| 读接口免登录 | ✅ 已经是（`SaTokenConfigure` 只拦写方法 + 少数 admin 读页） |
| 写接口非 admin → 403 | ✅ 已经是（`SaRouter.match(POST/PUT/PATCH/DELETE).check(role=admin)`） |
| 前端按权限位显隐按钮 | ✅ 已经是（`*:edit` 决定按钮显隐） |
| 登录 | ✅ 已有（admin 是当前唯一的写者） |
| **IP / User-Agent** | ❌ 没记 |
| **审计表** | ❌ 没有 |
| 403 的文案 | ❌ 现在只说"无权限"，不说"请联系管理员" |

**结论：Q1 真正要加的只有两样** —— 审计表 + 一句更清楚的 403 文案。拦截本身**不用新写**。

## 三、Q2：记录谁？我建议**不要加自注册**

⚠️ 使用方说"所以要新增一个注册功能" —— **这一步我建议停一下**，理由是：

- 匿名状态下**根本没有 username**。让匿名者"先注册再操作"，等于让他**自报姓名**，
  记下来的"谁"是不可信的 —— 审计记一个不可信的值，比记空更糟。
- 内部工具开自注册还会多一个攻击面（谁都能建号、能拿到什么权限要额外想）。

**可信的身份只有两种**：

1. **已登录的 admin** —— 有 username，可信；
2. **匿名者** —— 只能靠 **IP + User-Agent + 时间** 定位，这就是它可信度的上限，别假装更高。

⇒ 审计建议字段：

```
id / ip / user_agent / username(可空) / method / path /
target(表或文件前缀) / params_digest(参数摘要，不存正文) /
result(denied / success) / created_at
```

⇒ 若将来真需要"谁在写"，**让想写的人向管理员申请账号**（管理员开通，不是自注册）——
这和现有账号体系一致，也符合本项目"写操作只授 admin"的既定口径。

## 四、Q3：AOP 还是钩子？你**没落伍**，但两个词不是一回事

- **「钩子」** 是**前端框架**的生命周期概念（Vue 的 onMounted 之类），它管不到**数据库写**。
- **AOP** 是对的，**但别用它做"拦截"** —— 你**已经有**集中闸门 `SaTokenConfigure`。
  再写一个切面拦"是不是 admin"= 两处判断，迟早不一致（这正是 变更-096 权限收紧时踩过的路）。

**推荐的分工（各司其职，别叠床架屋）**：

| 职责 | 放哪 |
|---|---|
| 拦截（能不能写） | **保留在现有闸门**（一处） |
| 记录（谁想写） | `@AuditWrite("资料归档-新增")` 注解 + 一个 `@Around` 切面 |
| 落库 | **不要在切面里同步写表** —— 发 Spring 事件（`ApplicationEventPublisher`），由 `@Async` 监听器写审计表 |

最后一条是关键：审计写失败**不能连累业务**（业务成功、审计丢了 → 记日志补）；反过来
业务失败、审计写了也没什么损失。

**"前沿有没有更好的"** —— 有，但都是在这一套之上做减法/加固，不是换掉它：

1. **事件驱动 + 异步**（推荐，现代 Spring 的标准做法）
2. **outbox 表**：要求"审计绝不丢"时用（先写库、再异步投递）
3. **OpenTelemetry**：那是看**性能/链路**的，不是业务审计，别混用
4. **DB 触发器**：记不到"谁 + IP"，只有库内变更，不满足这个需求

⇒ 结论：**AOP + 注解 + 异步事件**，2026 年依然是标准且合适的做法。你没落伍，只是问题里混了两个词。

## 五、真要做的话，顺序（估）

1. `audit_write_attempt` 表（`docs/schema.sql` 第 24 步）
2. 闸门里"403 时发一个事件"（一行）
3. `@AuditWrite` 注解 + 切面（成功路径）
4. 前端 403 文案统一改成「此操作需要管理员，请联系…」（`api/request.js` 一处）
5. （可选）管理端一个审计查询页 —— 只给 admin

⚠️ **隐私**：IP + UA 属于个人数据。只给 admin 看；写清保留期（建议 180 天，到期清理）；
参数摘要**不存正文**（避免把资料内容/密码类字段抄进审计表）。

## 六、和现有设计的关系

- 与 **ADR-0005（采购登记只写库存表）** 不冲突 —— 那是数据归属，这是操作留痕。
- 与 **变更-126 的「全员可看」** 口径一致：读放开、写管住、越权有痕。
- **不要**做成"切面拦所有方法"：一个列表页刷三次 = 三条审计，表很快会爆。
